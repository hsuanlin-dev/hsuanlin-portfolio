# Debounce、Throttle 與併發控制都在限流，但守的不是同一條線

## TL;DR

在前端效能優化與非同步任務管理中，Debounce（防抖）、Throttle（節流）與 Concurrency Control（併發控制）經常被放在一起討論。它們都能避免系統在短時間內執行過多工作，但控制的其實是三種不同的問題：

* **Debounce：** 等待連續事件暫停後再執行，避免過早處理尚未確定的結果。
* **Throttle：** 限制函式在一定時間內的執行頻率，避免高頻事件造成過多運算。
* **Concurrency Control：** 限制同時進行的非同步任務數量，控制系統的資源負擔。

這三種策略並不是依照事件名稱分類，而是取決於實際需求：是否只需要最後結果、是否需要持續回應，以及是否需要限制同時進行的工作量。

而 JavaScript 的 Event Loop（事件循環），則是理解計時器、Promise 與非同步任務如何被安排執行的重要基礎。

---

## 1. 核心概念：想像一間只有一個店員的飲料店

在深入瀏覽器機制前，可以先用一間飲料店來理解三者的差異。

假設店裡只有一位負責處理訂單的店員，但他必須面對不同類型的工作。

### ① Debounce（防抖）：「等你想好再做」

顧客在點餐機上反覆修改訂單：先選珍珠、改成布丁，又改回珍珠。

如果每修改一次，店員就立即把訂單送進後廚，會產生許多不必要的工作。因此店員決定：等顧客停止修改一段時間，例如 300ms，才送出最後確認的訂單。

```
顧客修改訂單
    │
    ├── 0ms     選珍珠
    │           └── 開始計時 300ms
    │
    ├── 100ms   改布丁
    │           └── 取消計時，重新計時 300ms
    │
    ├── 200ms   改珍珠
    │           └── 取消計時，重新計時 300ms
    │
    └── 500ms   沒有新的修改
                │
                ▼
          送出珍珠訂單 ✓

結果：修改 3 次，實際送出 1 次
```

**核心思維：** 將短時間內連續發生的事件，收斂成事件暫停一段時間後的一次執行。

### ② Throttle（節流）：「定期處理，不必每次都做」

顧客等待飲料時，不斷按下叫號機的刷新按鈕。

如果每按一次就重新查詢並更新號碼，會產生許多重複工作。因此店員決定：即使顧客持續按下按鈕，也限制每秒最多處理一次刷新。

```
顧客不斷按下刷新按鈕

時間       按下刷新    實際更新
────────────────────────────────
0ms           ●           ✓
200ms         ●           ✕
400ms         ●           ✕
600ms         ●           ✕
800ms         ●           ✕
1000ms        ●           ✓
1200ms        ●           ✕
1400ms        ●           ✕
1600ms        ●           ✕
1800ms        ●           ✕
2000ms        ●           ✓
────────────────────────────────

結果：按下 11 次，實際更新 3 次
      兩次更新至少間隔 1 秒
```

這樣既能減少工作量，也能讓顧客在等待過程中持續看到更新。

**核心思維：** 事件可以持續發生，但函式不必每次都執行，而是在設定的時間間隔內限制執行頻率。

### ③ Concurrency Control（併發控制）：「事情很多，但同時只做幾件」

外送平台一次送來 50 杯飲料的訂單，但店裡只有 4 台搖搖機。

店員不會同時處理全部 50 杯，而是先安排 4 杯開始製作。每當一台機器完成工作，就從剩餘訂單中安排下一杯，不需要等待其他機器全部完成。

```
   外送平台一次送來 50 杯訂單
              │
              ▼
         等待處理的訂單
 [01][02][03][04][05] ... [50]
              │
              ▼
        同時最多處理 4 杯
   ┌────────────────────┐
   │ 機器 A：訂單 01     │
   │ 機器 B：訂單 02     │
   │ 機器 C：訂單 03     │
   │ 機器 D：訂單 04     │
   └────────────────────┘
              │
              ▼
         訂單 02 完成 ✓
              │
              ▼
       機器 B 接手下一杯
   ┌────────────────────┐
   │ 機器 A：訂單 01     │
   │ 機器 B：訂單 05 ←新 │
   │ 機器 C：訂單 03     │
   │ 機器 D：訂單 04     │
   └────────────────────┘
              │
              ▼
         持續完成與補位
              │
              ▼
        所有訂單處理完畢

結果：同時製作的飲料最多 4 杯
      每完成一杯，就能補上下一杯
```

**核心思維：** 不是減少需要處理的任務，而是限制同時進行的任務數量。

### ④ Event Loop（事件循環）：「店員如何安排手上的工作」

店員一次只能親自處理一件事情，但可以把飲料交給機器製作，等機器完成後再處理後續步驟。

JavaScript 的主執行緒也有類似特性：同步程式碼在呼叫堆疊（Call Stack）中執行，而計時器、網路請求等非同步操作可以由瀏覽器提供的機制協助處理。當非同步操作達到可以繼續執行的條件時，相關工作會依照排程規則等待 JavaScript 執行。

**核心思維：** Event Loop 不是限流策略，而是 JavaScript 執行環境協調任務、微任務及其他工作的重要機制。

需要注意的是，飲料店只是一種理解方式。瀏覽器並非真的只有一個工作單位，JavaScript 主執行緒以外也有其他機制負責計時、網路及部分背景工作。

## 2. 實戰場景：把飲料店換成瀏覽器

理解概念後，接著將三種策略應用到實際的前端系統，例如設備管理 Dashboard。

### ① Debounce 應用：搜尋輸入與視窗縮放

當使用者在搜尋框輸入關鍵字時，`input` 事件會隨每次輸入觸發。如果每打一個字就立即發送 API，可能產生大量不必要的中間查詢，增加網路與後端的處理負擔。

但對於只需要最終搜尋結果的功能，我們通常不必處理使用者輸入到一半的內容，而是希望等使用者暫時停止輸入後，再根據最後的關鍵字進行搜尋。

這正是 Debounce 的用途：每次事件發生時都重新計時，只有在指定時間內沒有新的事件，才真正執行函式。

```js
function debounce(fn, delay) {
  let timer = null;

  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const handleSearch = debounce((keyword) => {
  fetch(`/api/devices?q=${encodeURIComponent(keyword)}`)
    .then((response) => response.json())
    .then(renderDeviceList);
}, 300);

searchInput.addEventListener('input', (e) => {
  handleSearch(e.target.value);
});
```

另一個常見應用是 `window.resize`。例如某個複雜圖表需要根據視窗大小重新計算座標，如果不要求縮放過程中持續重新計算，就可以等使用者停止調整視窗後再執行，避免反覆進行昂貴運算。一般的響應式排版則應優先交由 CSS 處理。

**常見誤用：** 如果把這類只需要最終結果的操作改成 Throttle，系統仍可能在使用者持續輸入或縮放期間，定期執行不必要的中間查詢或計算。

這不代表 Throttle 不能用於搜尋或 Resize，而是當需求只在乎操作停止後的結果時，Debounce 通常更直接且有效率。

### ② Throttle 應用：拖曳、捲動與即時畫面更新

當使用者拖曳拓撲圖或捲動畫面時，`mousemove`、`scroll` 等事件可能在短時間內大量觸發。如果每次事件都執行複雜的座標計算或畫面更新，可能造成不必要的運算負擔，影響互動流暢度。

但這類操作與前面的搜尋案例有一個關鍵差異：使用者需要在操作過程中持續看到畫面變化，而不是等到操作結束後才看到結果。

因此，可以考慮使用 Throttle，限制函式的執行頻率，減少重複運算，同時保留持續的視覺回饋。

```js
function throttle(fn, interval) {
  let last = 0;

  return function (...args) {
    const now = Date.now();

    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

const handleDrag = throttle((x, y) => {
  renderTopology(x, y);
}, 100);

topologyCanvas.addEventListener('mousemove', (e) => {
  handleDrag(e.clientX, e.clientY);
});
```

上述範例每 100ms 最多執行一次，主要用來展示 Throttle 的時間間隔控制，而非完整的拖曳實作。

這種簡化方式會略過間隔內的事件，也不保證最後一次座標一定被更新。實務上，若需要更流暢的拖曳或動畫效果，通常會考慮使用 `requestAnimationFrame` 配合瀏覽器的繪製節奏。

**常見誤用：** 如果在需要持續視覺回饋的操作中使用 Debounce，只要事件不斷發生，計時器就會持續重設，畫面可能直到使用者停止操作後才更新，造成拖曳途中沒有反應、結束後才突然跳到最後位置的感覺。

兩者的選擇並不取決於事件名稱，而是互動需求：**只需要停止後的結果，優先考慮 Debounce；操作過程中仍需要持續回應，則可以考慮 Throttle。**

### ③ Concurrency Control 應用：批次操作與 Worker Pool

當使用者在設備管理列表中勾選 50 台裝置，並執行「批次重啟」時，系統需要發送 50 個獨立的 API 請求。

如果使用 `Promise.all()` 並一次啟動所有請求，可能在短時間內增加後端伺服器的處理負擔。

這時可以透過 Concurrency Control，限制同時進行的請求數量。例如將上限設定為 4，讓系統先執行 4 個任務，每當其中一個正常完成，就安排下一個。

這與前面飲料店的比喻相同：50 杯飲料代表 50 個任務，4 台搖搖機則代表 4 個 Worker。每台機器完成一杯後，就接手下一杯，而不必等待其他機器全部完成。這種管理方式稱為 **Worker Pool（工作者池）**。

```js
async function runWithLimit(tasks, limit) {
  if (!Number.isInteger(limit) || limit < 1) {
    throw new RangeError('limit must be a positive integer');
  }

  let index = 0;

  async function worker() {
    while (index < tasks.length) {
      const current = index++;
      await tasks[current]();
    }
  }

  const workers = Array.from(
    { length: Math.min(limit, tasks.length) },
    () => worker()
  );

  await Promise.all(workers);
}
```

實際應用：

```js
const tasks = selectedDevices.map((id) => {
  return async () => {
    const response = await fetch(
      `/api/device/${id}/restart`,
      { method: 'POST' }
    );

    if (!response.ok) {
      throw new Error(`Failed to restart device ${id}`);
    }
  };
});

await runWithLimit(tasks, 4);
```

這段程式碼的關鍵在於：`tasks` 儲存的是尚未執行的函式，而不是已經開始執行的 Promise。

`runWithLimit()` 最多建立 4 個 Worker。每個 Worker 透過 `await` 等待當前任務完成，再由 `while` 迴圈取得下一筆任務。

只要任務正常完成，Worker 就會持續補位，因此即使總共有 50 個任務，同時進行的數量仍不會超過 4 個。

這裡的 Worker 只是負責管理非同步任務的 async 函式，並不是瀏覽器的 Web Worker，也不代表建立了 4 條 JavaScript 執行緒。

**常見誤用：把 Throttle 當成併發控制**

Throttle 控制的是函式執行頻率，而不是同時進行的任務數量。例如：

```js
const throttledFetch = throttle((widgetId) => {
  fetch(`/api/widget/${widgetId}`)
    .then((response) => response.json())
    .then(renderWidget);
}, 100);

widgets.forEach((widget) => {
  throttledFetch(widget.id);
});
```

假設 10 個 Widget 幾乎同時呼叫同一個 `throttledFetch()`，以上方的簡易 Throttle 實作來說，第一個符合條件的呼叫會執行，其餘呼叫則可能因為時間間隔不足而直接被略過。

結果不是「10 個 Widget 排隊載入」，而是部分 Widget 根本沒有發送請求，導致資料缺失或載入狀態無法正常結束。

即使改用會延後執行的 Throttle，也不能保證同時進行的請求數量，因為前一個請求可能尚未完成，下一個請求就已經開始。

> **兩者的核心差異：Throttle 限制執行頻率；Concurrency Control 限制同時進行的任務數量。**

**工程權衡：Concurrency Limit 不是越大越好**

併發上限會影響整體完成時間與資源使用情況。

設定太低，例如 `limit: 1`，所有任務必須逐一等待，可能拉長整體完成時間；設定太高，例如 `limit: 50`，則可能讓大量請求同時抵達後端，增加伺服器負擔，甚至遇到限流或逾時問題。

因此，適當的併發上限應根據後端處理能力、網路條件與實際需求決定。

另外，併發控制不等於任務成功保證。

上述 Worker Pool 是簡化的教學範例。如果其中一個任務失敗，對應的 Worker 就會停止，外層 `Promise.all()` 也會進入 rejected 狀態；其他已啟動的 Worker 則不會自動取消。

正式的批次操作仍需要根據需求補上錯誤處理、重試策略與結果彙整，才能確保每個任務都有明確的執行結果。

## 3. 三條線，同一個執行環境

前面三種策略各自解決不同的問題，但當它們涉及計時器、Promise 或非同步請求時，就需要理解 JavaScript 執行環境如何安排工作。

### Event Loop：同步工作、Task 與 Microtask

在瀏覽器主執行緒中，JavaScript 同步程式碼會在 Call Stack（呼叫堆疊）中執行。

遇到 `setTimeout()` 時，瀏覽器會安排計時器；遇到 `fetch()` 時，網路請求可以透過瀏覽器的網路機制非同步進行。

這些操作不代表 JavaScript 必須停在原地等待。當對應條件達成時，後續工作會依照排程規則等待執行。

其中有兩種重要概念：

**Task（任務，也常被稱為 Macrotask）**

例如計時器到期後的回呼、部分使用者互動事件等，都會透過 Task 的排程機制執行。

`setTimeout(fn, 300)` 不保證函式一定在 300ms 時準時執行，而是在符合計時條件後，等待主執行緒有機會處理。

**Microtask（微任務）**

Promise 的 `.then()`、`.catch()`、`.finally()` 回呼，以及 `await` 之後的非同步函式續行，都會透過 Microtask 機制安排。

一般而言，當目前的 JavaScript 工作完成後，瀏覽器會進行 Microtask checkpoint，處理佇列中的微任務，再繼續後續工作。

不過，瀏覽器的排程並不只有這兩種機制，畫面繪製與 `requestAnimationFrame` 也有各自的執行時機。

### Debounce 與 Throttle 如何使用這些機制？

典型的 Debounce 會使用 `setTimeout()` 安排延後執行，並透過 `clearTimeout()` 取消先前尚未執行的計時器。每當新的事件到來，就重新計時，直到事件暫停一段時間，回呼才有機會執行。

Throttle 則有不同的實作方式。例如前面的版本使用 `Date.now()` 比較時間差，符合條件就直接執行函式，並沒有建立新的計時器。其他版本也可能使用 `setTimeout()` 延後執行。

因此，**Debounce 與 Throttle 是控制策略，而不是 Event Loop 內建的排程類型。** 它們是否涉及 Task Queue，取決於具體實作。

### 併發控制如何自動補位？

回頭看前面的 Worker Pool：

```js
async function worker() {
  while (index < tasks.length) {
    const current = index++;
    await tasks[current]();
  }
}
```

當 Worker 執行到 `await` 時，如果 Promise 尚未完成，非同步函式就會暫停後續執行，不會持續占用 JavaScript 呼叫堆疊。

等 Promise 完成後，`await` 後續的程式碼會透過 Microtask 安排恢復執行。Worker 恢復後，就能繼續 `while` 迴圈，取得下一個任務。這也是 Worker Pool 能在任務完成後自動補位的原因。

但需要區分兩件事：

* **Worker Pool：** 由程式碼決定補位規則，以及同時最多允許多少個任務進行。
* **JavaScript 執行環境：** 在非同步操作完成後，依照排程規則讓相關程式碼恢復執行。

因此，自動補位並不是 Event Loop 主動決定下一個任務，而是 Worker Pool 的程式邏輯，配合 Promise 與 JavaScript 排程機制所產生的結果。

它們都會使用 JavaScript 的執行機制，但本身並不是瀏覽器內建的三條獨立排程通道。

## 4. 總結與結構對比

| 概念 | 控制什麼 | 主要目的 | 常見應用 |
| --- | --- | --- | --- |
| Debounce | 連續事件暫停後的執行時機 | 避免過早處理中間狀態 | 搜尋輸入、縮放結束後計算 |
| Throttle | 一段時間內的執行頻率 | 降低高頻事件的處理成本 | 拖曳、捲動、持續更新 |
| Concurrency Control | 同時進行的任務數量 | 控制資源使用與系統負擔 | 批次 API、檔案上傳 |
| Event Loop | JavaScript 工作的執行排程 | 協調同步與非同步工作 | 計時器、Promise、事件處理 |

如果將它們轉換成實際開發中的判斷問題：

* **Debounce：** 使用者還在持續操作嗎？是否可以等他停止後再處理？
* **Throttle：** 事件發生得太頻繁了嗎？是否需要持續回應，但不必每次都執行？
* **Concurrency Control：** 這些任務是否都需要處理？系統同一時間可以承受多少個？
* **Event Loop：** 已經安排的 JavaScript 工作，會依照什麼機制與順序獲得執行機會？

這四個問題處理的層次不同，不能直接互相替代。

## 5. 結語

Debounce、Throttle 與 Concurrency Control 都能減少不必要的工作或控制系統負擔，但它們並不是同一種限流工具。

Debounce 關心的是連續事件何時應該觸發處理；Throttle 關心的是函式應該以多高的頻率執行；Concurrency Control 則關心同一時間允許多少個任務進行。

Event Loop 並不是第四種限流策略，而是理解這些控制邏輯如何與 JavaScript 非同步執行機制配合的重要基礎。

真正重要的不是記住哪個事件一定該用哪種工具，而是先判斷問題發生在哪個層次，再選擇對應的控制方式。

看清每種策略的職責，才能在回應速度、畫面流暢度與資源效率之間，做出合理的工程權衡。
