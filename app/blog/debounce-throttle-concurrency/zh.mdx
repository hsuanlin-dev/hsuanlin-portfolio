# Debounce、Throttle 與併發控制都在限流，但守的不是同一條線

## 1. TL;DR

在前端效能優化與資源調度的領域中，Debounce（防抖）、Throttle（節流）與併發控制（Concurrency Control）常被粗略地歸類為同一種「限制流量」的手段。然而，這三個工具在設計哲學上，各自守護著完全不同的觸發來源：**使用者輸入、畫面渲染、任務數量**。

在開發複雜的前端應用（如大型網格系統、即時監控儀表板）時，混用工具的代價通常不是程式碼寫不出來，而是使用者體驗或後端硬體資源會在特定極端情境下無預警地崩潰。而底層的事件循環（Event Loop），則是讓這三種策略能在單執行緒的世界裡和平共存、互不干涉的終極解答。

## 2. 核心概念剖析：想像一間只有一個店員的飲料店

在深入瀏覽器機制前，我們可以用一個生活化的「單人飲料店」情境來直覺理解這三者的分工。這家店只有一位店員（JavaScript 單執行緒），他必須面對不同的流量挑戰：

### ① Debounce（防抖）：「等你想好再做」

顧客在點餐機上反覆修改訂單：先選珍珠，又改成布丁，又改回珍珠。店員不會每次你按一下就把單子送進後廚，而是等你「停手」一段時間（比如 0.3 秒沒再按）之後，才把最終那一版訂單送出。

**核心思維**：將一連串高頻的「連續修改動作」，收斂成最後一次的定案結果。

### ② Throttle（節流）：「定時看一次，不要每次都看」

顧客排隊時拚命按叫號機的「刷新」按鈕想看現在叫到幾號。如果每按一次就重新整理畫面，店員會被煩死。所以規定：不管你按幾次，畫面每隔 1 秒才更新一次最新號碼。

**核心思維**：事件依然在高頻發生，但人為降低系統的反應頻率，定期抓取最新狀態即可。

### ③ 併發控制（Concurrency Control）：「事情很多，但同時只做幾件」

外送平台瞬間湧入了 50 杯飲料的訂單（任務數量已確定），但店裡只有 4 台搖搖機。店員絕不能把 50 杯同時塞給機器（硬體會瞬間過載或損壞），而是先讓 4 杯開始搖，哪一台機器先搖好，就馬上下架並補上下一杯，永遠保持線上只有 4 杯在跑。

**核心思維**：任務總量已經確定，管的是「同時執行的通道上限」，與使用者的操作速度完全無關。

### ④ Event Loop（事件循環）：「店員只有一個人，他怎麼分配時間」

店員（主執行緒）不可能同時做兩件事。但他腦中有一張清單在反覆循環檢查：「手上這件事做完了嗎？鬧鐘響了嗎？搖搖機跳起來了嗎？」他永遠遵循固定的調度規則：先把手上的同步工作做完，再絕對優先處理插隊的微任務（Microtask，如 Promise 完成），最後才輪到排隊的宏任務（Macrotask，如 `setTimeout`）。

**核心思維**：它不是一種優化策略，而是背後讓前三者真正動起來的「物理引擎」。

## 3. 實戰場景還原：把飲料店換成瀏覽器

當我們把上述情境還原至現代前端架構（例如設備管理 Dashboard），這三道限流策略將各自鎮守不同的關卡：

### ① Debounce 應用：搜尋／篩選框的 API 優化

當使用者在全域搜尋框輸入關鍵字尋找特定機房設備時，若直接監聽 `input` 事件發送請求，每打一個字就送一次 API，後端伺服器會瞬間承受不必要的壓力。此處需要防抖，等待使用者真正停手才發送最終關鍵字。

```js
function debounce(fn, delay) {
  let timer = null;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

const handleSearch = debounce((keyword) => {
  fetch(`/api/devices?q=${keyword}`).then(renderDeviceList);
}, 300);

searchInput.addEventListener('input', (e) => handleSearch(e.target.value));
```

**🚨 誤區代價**：若在此處誤用節流（Throttle），代價雖然不會讓系統崩潰，但會造成嚴重的頻寬浪費。使用者在連續輸入的過程中，系統依然會按固定的時間間隔強制送出「中間狀態」的搜尋請求，而這些未完成的請求在送出的那一刻就注定被浪費，因為等回應回來時，輸入框的關鍵字早就改變了。

### ② Throttle 應用：Widget Resize 與拖曳即時渲染

使用者在操作拓撲圖（Topology Canvas）進行拖曳或縮放時，`mousemove` 事件一秒內能觸發數十次。如果每次觸發都讓 React 重新計算大量節點座標並重繪 DOM，網頁畫面會立刻掉幀（Lag）。

```js
function throttle(fn, interval) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      fn.apply(this, args);
    }
  };
}

const handleDrag = throttle((x, y) => {
  renderTopology(x, y);
}, 100);

topologyCanvas.addEventListener('mousemove', (e) => handleDrag(e.clientX, e.clientY));
```

**🚨 誤區代價**：把該用節流的場景換成防抖（Debounce），通常是 UI 互動的災難。每一次 `mousemove` 觸發時，Debounce 都會把上一個計時器清掉並重新排隊。使用者的滑鼠只要還在移動，計時器就永遠撐不到倒數結束，導致渲染函式在拖曳結束放手前完全沒機會被呼叫。體感上就會呈現「拖曳時畫面完全凍結，鬆手那一瞬間才突然跳一下」的詭異當機感。

### ③ 併發控制應用：批次操作觸發大量 Fetch

當使用者在列表勾選 50 台裝置並點擊「批次重啟」，或是複雜頁面一打開、10 個獨立的 Widget 組件同時打自己的 API 抓資料時，如果直接使用 `Promise.all` 一口氣全發，瞬間發射的請求會立刻撞上瀏覽器的同網域連線限制（HTTP/1.1 通常上限為 6 個），甚至癱瘓後端的處理能力。這時必須引入併發控制（Worker Pool），將任務限額分批送出，在保護系統通道的前提下，依序完成所有任務。

```js
// 穩健的非同步併發控制實作
async function runWithLimit(tasks, limit) {
  let index = 0;

  async function worker() {
    while (index < tasks.length) {
      const current = index++;
      // 等待當前任務執行完畢（走微任務佇列排程），再自動補位下一件
      await tasks[current]();
    }
  }

  // 建立指定數量的並行工作軌道（Worker Pool）
  await Promise.all(Array.from({ length: limit }, worker));
}

// 實務應用：批次重啟 50 台裝置
const tasks = selectedDevices.map((id) => () => fetch(`/api/device/${id}/restart`));
runWithLimit(tasks, 4); // 限制永遠只有 4 個請求在通道上並行
```

**🚨 致命誤區：把非同步併發控制換成節流（Throttle）**

這是一個非常隱蔽且嚴重的邏輯錯誤。在這個場景下誤用工具，代價不是效能慢一點，而是核心資料會直接被遺失，且系統完全不會報錯。這兩者的核心設計哲學完全相反：

* **節流允許丟棄（Time-based）**：使用者拖曳拓撲圖時，漏掉幾次 `mousemove` 的座標取樣沒有任何代價，因為下一次取樣很快就到。它的思維是：「我只要最新狀態，中間漏掉的無所謂。」
* **併發控制絕不允許丟棄（Capacity-based）**：10 個 Widget 各自的初始化資料、50 台設備的重啟指令，每一個都是必須安全送達、獨立且不可或缺的核心任務。它的思維是：「每一個任務都必須執行成功，我只是要限制它們不要同時發生。」

```js
// 錯誤示範：企圖用節流來限流 Widget 的載入請求
const throttledFetch = throttle((widgetId) => {
  fetch(`/api/widget/${widgetId}`).then(renderWidget);
}, 100);

// 10 個獨立的組件在頁面初始化時，幾乎同時呼叫 throttledFetch
widgets.forEach((w) => throttledFetch(w.id));
```

這 10 次呼叫幾乎發生在同一個事件循環的週期（Tick）內。由於節流的判斷邏輯只看「時間差」，當第一個 Widget 的請求成功通過後，接下來 9 個請求的時間差都不滿足間隔條件，它們會被節流函數直接「丟棄」，而不是延後執行。

反映在 UI 上的結果是：頁面加載後，只有第一張卡片順利出現資料，其餘 9 張卡片永遠卡在轉圈圈的 Loading 狀態。此時不論是瀏覽器 Console 還是 Network 都不會有任何錯誤訊息，開發者必須花費大量時間通宵排查，才會意識到那些請求從一開始就根本沒有被送出。

### 工程權衡（Trade-off）與參數配置

實作併發控制時，`limit` 參數的配置並非越高越好，它極度考驗工程師對系統資源的權衡思考：

* **設定得太低（例如 `limit: 1`）**：十個 Widget 會排成長龍，引發線頭阻塞（Head-of-Line Blocking），使用者會明顯感受到頁面區塊局部載入的嚴重卡頓。
* **設定得太高（例如 `limit: 50`）**：則讓這道防線流於形式，瞬間湧入的連線會直接撞擊瀏覽器的物理上限或打爆後台硬體能力，任務最終開始陸續逾時（Timeout）宣告失敗。

## 4. 三條線，同一個引擎

防抖守著使用者輸入，節流守著畫面渲染，併發控制守著任務數量：三條防線，各自獨立，互不隸屬。然而，不論我們在前端寫了多麼完美的防禦策略，最終都必須回歸到同一個底層核心，也就是 JavaScript Runtime 引擎。我們可以用這張架構圖，直覺地看清這三條防線在底層是怎麼運作的：

### 雙軌排程：宏任務與微任務的匯流

防抖、節流、併發控制活在同一個 JS 主執行緒（Call Stack）裡。它們之所以能和平共存而不互相打結，是因為它們使用的瀏覽器 API，在底層巧妙地走進了不同的雙軌排程路徑：

* **防抖（Debounce）與節流（Throttle）走「宏任務」路徑。** 它們的核心實作都依賴 `setTimeout`。當瀏覽器 Web APIs 計時結束後，完成的回呼（Callback）依規定會被推進右下角的宏任務佇列（Macrotask Queue）中排隊。
* **併發控制（Concurrency Control）走「微任務」路徑。** 它管的是網路請求（如 `fetch`），並依賴 Promise（或 `await`）來感知任務的結束。當非同步請求 Resolve 的瞬間，對應的回呼會直接進入優先權更高的微任務佇列（Microtask Queue）。

### 幕後推手：併發控制的調度錯覺

這解開了併發控制最容易被誤解的地方。它表面上看起來很聰明，能自己執行調度：做完一個、自動補上一個。但只要對照架構圖那條橫跨整個 Runtime 的紅色虛線閉環（併發調度閉環），你就會發現：本質上，**併發控制只決定了「補位規則」，它根本無法決定「補位的精確時間點」**。

當程式碼發出 `fetch` 並暫停在 `await` 那一行時，主執行緒的控制權就交給了 Web APIs。這個任務必須在網路請求完成、回呼進入微任務佇列排隊，最後由底層的事件循環（Event Loop）偵測到堆疊空了、將回呼重新拉回呼叫堆疊（Call Stack）的那一刻，下一個任務的補位動作才真正被按下執行鍵。也就是說，那條紅色的大型閉環動線，才是讓併發控制產生「自動調度錯覺」的真正幕後推手。

## 5. 總結與結構對比

| 概念 | 管的是什麼 | 觸發來源 | 保護的是誰 | 執行在哪裡 |
| --- | --- | --- | --- | --- |
| Debounce | 收斂成「最後一次」 | 使用者輸入（不可控頻率） | 避免不必要的重複請求 | 瀏覽器 JS 主執行緒 |
| Throttle | 降頻成「定期一次」 | 高頻事件（不可控頻率） | 畫面渲染效能 | 瀏覽器 JS 主執行緒 |
| 併發控制 | 限制「同時幾件」 | 任務數量已確定，只觸發一次 | 瀏覽器連線上限／後端伺服器資源 | 瀏覽器 JS 主執行緒 |
| Event Loop | 排程「誰先誰後」 | 全部都要靠它執行 | — | JS 引擎底層 |

## 6. 結語

在前線，防抖、節流、併發控制是我們的「戰術策略」，決定了任務要不要做、什麼時候做、以及同時做幾件。而在後方，Event Loop 則是唯一的「物理引擎」。沒有這個引擎在底層轉圈圈，前三者的計時器和 Promise 都只是躺在記憶體裡、永遠不會被執行的死程式碼。

在開發複雜的前端系統時，看清它們各自守在哪一條防線上，遠比背熟任何一段 Polyfill 的寫法更重要。三條防線從頭到尾都不是同一條線，但讓它們真正跑起來、讓應用程式優雅運作的，從頭到尾都是同一個引擎。
